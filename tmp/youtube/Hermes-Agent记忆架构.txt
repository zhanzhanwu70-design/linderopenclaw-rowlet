主代理每次都會自覺的調用Memory工具
所以系統提示裡一直在灌輸Memory Guidance
提醒模型優先保存用戶偏好
環境怪癖 穩定約定
不要把Task Progress和Completed Work Log寫進去
這是一層前置約束
但它還不只這一層
Hermes Since Memory 會持續技術
如果連續很多輪都沒有發生Memory寫入
達到預值以後就觸發Background Review
默認預值是10輪
這個Background Review 會Folk一個輕量Review Agent
沿用當前模型把剛剛這段繪畫快照再過一遍
然後附加一段專門的Review Prompt
讓它自己檢查剛才有沒有什麼
本該記住卻沒記下來的事實
而且這個Review是在用戶已經收到最終回復之後
才一步跑的
目的是不跟主任務搶注意力
我很喜歡這個設計
因為它像一個會後秘書
主代理在前台把任務做完
後台在有人幫你檢查
剛才有沒有什麼值得長期沉澱的東西
這會讓記憶系統從單次工具決策
變成前台執行加後台復盤的雙重機制
容錯率會高很多
如果讓我概括Hermes當前這套機制架構最大的優點
我會說它的優點不是某一個Memory Background特別先進
而是邊界真的滑得很清楚
什麼是穩定事實
什麼是完整歷史
什麼是臨時召回
什麼是當前工作上下文
什麼是壓縮前必須搶著的信息
什麼是子代理不該碰的共享長期記憶
這些邊界基本都被顯示建模了
很多Agent系統最後不是輸在能力不夠
而是輸在上下文層次混了
歷史污染了
Session邊界不清楚
Hermes目前最大的價值
就是他沒有在這些地方偷懶
但他的局限也一樣很清楚
第一
內建Memory下次Session才生效
這會帶來明顯的體感之後
第二
Created Memory仍然只是文本條目
透明歸透明
但結構化治理不夠強
不容易做衝突檢測
自斷級合併和優先級管理
第三
Session Search更像摘要式回憶
適合回答上次發生了什麼
但還不夠適合Agent繼續拿他做結構化之心
第四
內建Memory和外部Provider之間
現在仍然是弱偶和
只能橋接
不是強一致
如果一定要說下一步最值得補什麼
我覺得重點不一定是
再接一個新的Memory Backend
更有價值的方向
反而是給Created Memory
加一點輕量結構化原信息
比如Scope
來源
更新時間
致信度
再就是做一個Session內可見
但不打碎System Prompt前綴的Overlay記憶層
這樣一來
既能保持現在的緩存策略
又能緩解我明明剛記住
為什麼當前Session還看不到的體驗問題
另外一條我覺得很值得做的
是把Session Search
從摘要模式繼續往前退一步
比如除了Semory
再加Artifact
Command
Decisions
這種結構化提取模式
因為Agent真正需要的
很多時候不是上次聊了什麼
而是上次到底執行了哪些命令
改了哪些文件
做了什麼決定
從現在這套Transcript的基座看
這條眼睛路徑其實是成立的
如果是你來繼續做這套系統
你會優先補結構化Curated Memory
還是補本Session可見的Overlay記憶
為什麼
所以回到最開始那個問題
Hermes到底是不是有一個很強的記憶模塊
我覺得更準確的說法是
它不是一個腦子
而是一個記憶工廠
Memory Markdown文檔和User Markdown文檔
是長期檔案規
State.db是完整流水帳
Session Search是檔案檢索員
外部Provider是可插拔的專業記憶後端
Flush Memories是上下文丟事前的歸黨員
Background Review則向事後副攀員
Arrone Conversation真正做的事情
是在不同邊界點把這些角色調度起來
讓他們各幹各的活
從Agent Engineering的角度講
這種設計不一定是最統一最優雅的
它甚至保留了不少眼鏡中的痕跡
比如Jayson Lines和Secretto並存
內建Memory Store和外部Provider並行存在
但也正因為它沒有為了抽象統一去強行簡化現實
所以它反而更接近一個真實複雜系統
在生產環境裡能長期工作的樣子
我會把它看成一種很有意識的系統及折中
而不是功能拼裝
如果你要用一句話總結Hermes的記憶架構
我覺得可以這麼說
它不是在追求什麼都記住
而是在追求把不同類型的記憶放進不同層次
用合適的生命週期和成本模型去管理它們
也正因為這樣
Hermes的價值不只是做了一個Memory Tool
而是把長期事實、完整歷史、外部Recall
還有壓縮和重置這些邊界事件
真正組織成了一套能落地、能擴展
也能自我約束的記憶基礎設施
