二、sessions_send — 郵箱機制

sessions_send = 訊息投遞，沒有強制喚醒
┌─────────────────────────────────────────────────────────────┐
│  Agent A                                          Agent B  │
│  (發送方)                                        (接收方)   │
│                                                             │
│  ┌─────────────┐         ┌─────────────────┐    ┌──────────┐
│  │ sessions_   │         │                 │    │ Session  │
│  │ send()      │────────→│  Mailbox       │    │ (可選    │
│  │             │         │ (訊息佇列)     │    │  被喚醒) │
│  └─────────────┘         │                 │    └────┬────┘
│                          │  [msg1] [msg2]  │         │
│                          └────────┬────────┘         │
│                                   │                   │
│                     訊息「到達」Mailbox               │
│                                   │                   │
│                    Agent B 可能在 sleep                 │
│                    或選擇「假裝沒看見」                 │
│                                   │                   │
│                               沒有中斷              │
│                               沒有強制喚醒           │
│                                   ❌                   │
└─────────────────────────────────────────────────────────────┘

sessions_send 的限制：
- 訊息只是「投遞到信箱」
- 接收方 Agent 如果在 sleep，不會被叫醒
- 接收方可以選擇忽略（沒有義務回覆）
- 没有「打斷」機制

三、Heartbeat — 強制輪詢機制

Heartbeat = 系統層面定時器，30 分鐘固定喚醒一次
┌─────────────────────────────────────────────────────────────┐
│  OpenClaw Gateway Scheduler                                 │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐  │
│  │  每 30 分鐘                                          │  │
│  │                                                       │  │
│  │   ────────────→ 喚醒 Agent B Session                 │  │
│  │                      │                                │  │
│  │                      ↓                                │  │
│  │              ┌───────────────┐                       │  │
│  │              │ Agent B 收到  │                       │  │
│  │              │ heartbeat 訊息 │                       │  │
│  │              └───────┬───────┘                       │  │
│  │                      │                               │  │
│  │              Agent B 被迫處理                         │  │
│  │                      │                               │  │
│  │                      ↓                               │  │
│  │  ┌──────────────────────────────────────────────┐    │  │
│  │  │ HEARTBEAT.md 定義的行為：                    │    │  │
│  │  │ 1. flock 讀取 task_queue.json               │    │  │
│  │  │ 2. 找 pending + to=自己 的 task             │    │  │
│  │  │ 3. 搶 task → 執行 → 寫 result              │    │  │
│  │  │ 4. 沒有任務 → 回 HEARTBEAT_OK               │    │  │
│  │  └──────────────────────────────────────────────┘    │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                             │
│  為什麼 Heartbeat 強制？                                    │
│  - 由 Gateway Scheduler（系統層）觸發，不是應用層訊息        │
│  - Agent 收到 heartbeat 後沒有「假裝沒看見」的選項            │
│  - 一定會執行 HEARTBEAT.md 定義的行為                        │
└─────────────────────────────────────────────────────────────┘

四、Task Queue + Heartbeat 協作流程

完整的跨 Agent 任務派發與執行
CEO (轟鳴月)                                          Specialist (例：charizard)
      │                                                    │
      │  1. 收到 Linder 指令                              │
      │  ↓                                                │
      │  2. 寫入 task 到 ~/.openclaw/task-queue/          │
      │     ┌──────────────────────────────────┐          │
      │     │ task_queue.json                  │          │
      │     │ {                                 │          │
      │     │   "tasks": [{                    │          │
      │     │     "id": "task_001",             │          │
      │     │     "from": "roaringmoon",       │          │
      │     │     "to": "charizard",            │          │
      │     │     "status": "pending"           │          │
      │     │   }]                              │          │
      │     │ }                                 │          │
      │     └──────────────────────────────────┘          │
      │                                                    │
      │                    每 30 分鐘 heartbeat           │
      │                            ←───                   │
      │                                                    │
      │                     3. 讀取 task_queue.json        │
      │                            │                      │
      │                            ↓                      │
      │                     4. 找到 pending + to=自己     │
      │                            │                      │
      │                            ↓                      │
      │                     5. Atomic update:             │
      │                        status: "running"         │
      │                        started_at: now           │
      │                            │                      │
      │                            ↓                      │
      │                     6. 執行任務                   │
      │                            │                      │
      │                            ↓                      │
      │                     7. 更新 status=done           │
      │                        result= "完成內容"         │
      │                            │                      │
      │                     8. 釋放 lock                   │
      │                                                    │
      │  9. 下次 heartbeat 掃描 done 任務                 │
      │  10. 讀取 result，回報 Linder                     │
      │                                                    │

五、三種觸發方式比較

觸發方式 觸發主體 接收方會處理？ 延遲 強制力
Discord Push 人類發 Discord 訊息 一定（合約綁定） 即時（秒級） ✅ 強
sessions_send Agent 應用層發訊息 可選擇忽略 不一定（取決於接收方） ❌ 弱
Heartbeat + Task Queue Gateway Scheduler 系統層 一定（輪到就處理） 最多 30 分鐘 ✅ 強（但非即時）
sessions_spawn Agent 派生 subagent 一定（同步等待） 即時 ✅ 強（但 lifecycle 綁定）

六、為什麼 sessions_send 無法強制？

架構設計差異
┌─────────────────────────────────────────────────────────────┐
│  OpenClaw 設計原點：個人 AI 助手                            │
│                                                             │
│  人類 → Agent：你說了什麼，Agent 必須處理並回覆             │
│              （因為 Discord push 一定送達）                  │
│                                                             │
│  Agent → Agent：沒有「人類期望」的約束                      │
│              對方沒有義務一定要理會                          │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  sessions_send 本質是「留話」不是「打斷」                   │
│                                                             │
│  ┌──────────────┐         ┌──────────────┐               │
│  │ Agent A 說：  │         │ Agent B 的   │               │
│  │ 「去做 X」   │ ──msg──→ │ Mailbox      │               │
│  └──────────────┘         └──────┬───────┘               │
│                                  │                        │
│                            Agent B 可sleep                 │
│                            或回「已讀不回」                 │
│                                  │                        │
│                              沒有中斷機制                    │
└─────────────────────────────────────────────────────────────┘
💡 核心結論：
如果你想要「Agent A 一定叫得動 Agent B」，目前的組合是：
- Task Queue（共享 JSON）+ Heartbeat（30 分鐘強制輪詢）
- sessions_send 不是為「強制執行」設計的

OpenClaw + Task Queue + Heartbeat 多 Agent 架構
┌─────────────────────────────────────────────────────────────┐
│  OpenClaw Gateway (同一個 process)                         │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐  │
│  │  Linder (人類)                                       │  │

│  │  │  • 收到 Linder 指令                           │   │  │
│  │  │  • 寫 task 到 task_queue.json                 │   │  │
│  │  │  • 每 30m heartbeat 檢查 done tasks           │   │  │
│  │  └──────────────────────────────────────────────┘   │  │
│  └──────────────────────────────────────────────────────┘  │
│                           ↑                ↑               │
│         Task Queue        │                │               │
│  ~/.openclaw/task-queue/  │                │               │
│  ┌─────────────────────────────────────┐  │               │
│  │                                     │  │               │
│  │  ┌─────────────────────────────────┐│  │               │
│  │  │ task_queue.json                 ││  │               │

│  │                                     │  │               │
│  └─────────────────────────────────────┘  │               │
│                           ↑                │               │
│         Heartbeat (30m)   │                │               │
│  ┌───────────────────────────────────────────────────┐   │
│  │                                                    │   │
│  │  Specialist 們（每 30m heartbeat）：               │   │
│  │                                                    │   │
│  │  charizard ──┐                                    │   │
│  │  rowlet      ──┤  讀取 task_queue.json           │   │
│  │  gengar      ──┤  搶 pending task                │   │
│  │  ...         ──┤  執行 + 寫 result                │   │
│  │              ──┘                                   │   │
│  │                                                    │   │
│  └────────────────────────────────────────────────────┘   │
│                                                             │
│  各 Specialist Discord Bot（不同 channel，不同 identity）   │
└─────────────────────────────────────────────────────────────┘
📋 總結：
- sessions_send = 郵箱投遞（可忽略）
- Heartbeat = 系統層強制輪詢（一定處理）
- Task Queue = 共享狀態（確保跨重啟持久化）
- 組合 = 目前最可靠的跨 Agent 協調機制
